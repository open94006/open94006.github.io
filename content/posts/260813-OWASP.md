OWASP 全名 **Open Web Application Security Project**，翻譯成中文就是「開放網路軟體安全計畫」，是個開放社群、非營利性組織，全球目前有數百個分會。

而 OWASP Top 10 是 OWASP 每隔幾年會公布的十大應用程式資訊安全風險清單，它不只寫給開發人員與資安部門，也讓決策者與大眾了解到，當今會在應用系統上主流遇到的資安問題，該如何預防、找出漏洞的建議指南。

> 以下根據 OWASP Top 10 2025 版本來介紹

## 1. 存取控制失效 Broken Access Control

### 這個問題怎麼發生

- IDOR（不安全物件參考）：使用者透過竄改網址或參數中的 ID（如`?id=101`改為 102），直接讀取或修改其他人的私密資料。
- 垂直越權：一般使用者透過猜測或強行瀏覽（Forced Browsing）進入管理員專屬頁面。
- 水平越權：登入系統後，以自身權限去操作或請求屬於其他同級使用者的業務功能。
- API 缺乏防護：未對後端介面的 POST、PUT、DELETE 請求進行嚴格的身分與權限驗證。

### 在 Node.js 裡我會怎麼防

要做到**預設拒絕（Deny by Default）**，讓新增的路由自動被保護，而不是每條路由各自設想怎麼加。

製作一個中介層 `authMiddleware`，此服務本身只做「有沒有登入」的驗證（如 JWT 簽章、過期），並加入到欲保護的路由，如訂單、使用者資料等。

```ts
app.use('/api', authMiddleware, apiRouter);
```

每個 `controller` 一律用 `req.user.id`／`req.user.user_id` 來當作該服務的第一個參數，或是判斷使用者身份，這是從 JWT 解出來，驗簽時如果有鎖死演算法，前端傳不了假的。

每一條會動到資源的 SQL，不管 SELECT/UPDATE/DELETE，都把 `user_id = $N` 跟資源自己的 id 一起放進 WHERE；如果是用 ORM，也一樣要確保 `find` 的參數中要包含使用者身份的篩選，才不會出現使用者以外的資料被撈取或被更新。

上述做法如果有預防到，即使把 URL 裡的 order_no 換成別人的（`GET /order/r/:order_no`），因為 SQL 子查詢多了 `AND user_id = $1`，查不到就是空的，不會洩漏或誤改別人資料。

至於未使用、測試用的路由，正式版一定要移除；最末端再放一個 catch-all 收尾，統一回應 404。

```ts
// 處理所有未匹配的請求，貫徹 Deny by Default
// '(.*)' 是 Express 5 的寫法
app.use('(.*)', (req, res) => {
    res.status(404).json({ message: '資源不存在或無存取權限' });
});
```

## 2. 安全設定錯誤 Security Misconfiguration

### 這個問題怎麼發生

- 未改預設值：保留出廠預設帳號與密碼。
- 權限過大：賦予使用者或服務過多的系統存取權限。
- 功能全開：安裝了不需要的服務、範例程式或未使用的連接埠。
- 資訊外洩：在正式環境中開啟偵錯模式（Debug Mode），導致系統架構與機敏資料曝光。
- 未定時更新：未修補框架、元件、函式庫的安全設定。

### 在 Node.js 裡我會怎麼防

1. 最小權限原則：只給予帳號或服務運作所需的最低權限，遇到沒有明確的指令**一律拒絕**，這無論是從資料庫層面，或是到應用層設計給後台系統不同身分人員登入時，都可以作為給予權限時的基本原則

2. 環境分離：確保測試（Development）與正式（Production）環境的設定完全隔離，可以用不同的環境檔和設置來避免衝突

3. 重要鍵值不重複使用：密鑰、pepper、JWT secret、資料庫密碼各自獨立，不共用同一組亂數

## 3. 軟體供應鏈失效 Software Supply Chain Failures

### 這個問題怎麼發生

- 隱藏依賴：會出現專案直接引用的套件，可能還包含許多層遞性相依套件，只要其中一個上游元件被駭，就會連帶遭受汙染。
- 缺乏變更追蹤：未記錄與防範開發環境、程式碼儲存庫，或是多套件管理工具（`npm` / `pnpm`）在同一個目錄混用，各自生成一份鎖檔，兩份鎖檔記錄的版本會隨時間各自漂移，沒人知道哪一份才是「真正在跑的那份」

### 在 Node.js 裡我會怎麼防

1. 一個 repo 只認一套套件管理工具：
    - `package-lock.json` 和 `pnpm-lock.yaml` 只會留下一個，其他工具的鎖檔一律刪掉
    - 把要移除的舊鎖檔名稱，加入到 `.gitignore`。並防止再次使用 `npm install` 加回來，在 `package.json` 加上 `"packageManager": "pnpm@x.y.z"` 並搭配 corepack，或用 `only-allow` 當 preinstall，用錯工具會直接在安裝時報錯。

2. 定期跑 `audit` 指令，或是接 Dependabot 等自動化工具，遍歷一次鎖檔內釘住的版本有沒有新出現的問題，並追蹤套件的更新趨勢，最新的版本也可能含有漏洞。

## 4. 加密機制失效 Cryptographic Failures

### 這個問題怎麼發生

- 明文傳輸或儲存：敏感資料（如密碼、信用卡號）**未經加密或雜湊**就直接採用、寫入資料庫或透過 HTTP 明文傳輸。
- 使用已淘汰的演算法：雜湊函數如`MD5`、`SHA-1`，或加密演算法如舊版`RC4`。另外`SHA-256`雖然未被破解，但速度太快，同樣不適合拿來存密碼。
- 金鑰管理不良：金鑰強度不足、直接寫死在程式碼（Hardcoded）中，或沒有定期更換。
- 時序攻擊：攻擊者使用逐字比對、時間微差、統計分析的方式，找出密碼驗證規律加以破解。

### 在 Node.js 裡我會怎麼防

1. 先分清楚用途再選演算法：可還原的加密用 `AES-256-GCM`（要選 authenticated encryption）、完整性驗證用 `HMAC-SHA256`、密碼儲存用 `argon2id`（我的專案採用的就是這個）或 `bcrypt`

2. 全面啟用 HTTPS，確保所有網路傳輸都透過 TLS 1.2+ / 1.3；如果是金融和電商，則需要**加上 HSTS，讓瀏覽器記住此站只走 HTTPS**，防止半路攔截。

3. 在時序攻擊（Timing Attack）上，我會採用固定時間比較，使用具備常數時間（Constant-Time）特性的比較函數，避免判斷結果提早返回。

```ts
crypto.timingSafeEqual(a, b);
```

## 5. 注入攻擊 Injection

### 這個問題怎麼發生

攻擊者把惡意程式碼、指令或提示詞塞入系統的輸入欄位中。可能是透過：

- 表單字串鍵入 **SQL 語法**送出，系統沒有檢查清楚，直接執行命令
- 透過惡意塞入的**跨網站指令碼（XSS）**
- 平台提供的 AI agent 或問答，透過**提示詞**推敲惡意攻擊

導致洩漏機密資料、Cookie、修改資料庫數據或控制整個程式。

### 在 Node.js 裡我會怎麼防

#### SQL Injection

採用主流 ORM (Prisma, Drizzle) 可以做到第一線基本的 SQL 注入防禦
如果為了效能或可控性，即使偏好使用原生 SQL，也應一律使用參數化查詢（Prepared Statements）

```ts
await client.query(
    `INSERT INTO b_order(user_id, order_no) VALUES ($1, $2) RETURNING id;
    `,
    [user_id, orderNo], // 使用參數來查詢或更新
);
```

對於無法參數化的 SQL 識別字（例如欄位名、資料表名、排序方向），則採用 switch 或白名單映射，硬性判斷其識別字，而不是直接使用使用者輸入。這樣能兼顧 SQL 的靈活性與安全性。

```ts
if (query.orderString) {
    switch (query.orderString) {
        case 'created_time_desc':
            orderBy = 'ORDER BY created_time DESC';
            break;
        case 'created_time_asc':
            orderBy = 'ORDER BY created_time ASC';
            break;
        case 'next_charge_at_desc':
            orderBy = 'ORDER BY next_charge_at DESC';
            break;
        case 'next_charge_at_asc':
            orderBy = 'ORDER BY next_charge_at ASC';
            break;
        default:
            break;
    }
}
```

#### 跨網站指令碼（XSS）

XSS 分成三種：

- **儲存型**（惡意碼寫進資料庫，每個看到該頁的人都中）
- **反射型**（惡意碼夾在網址裡，需誘導點擊）
- **DOM 型**（惡意碼沒送到後端，純在前端 JS 被執行）

可以從輸入端做格式驗證：型別、長度、白名單，例如 email 就必須長得像 email。輸出端做跳脫編碼，把 `<`、`>` 轉成 `&lt;`、`&gt;`；編碼方式要看輸出位置，HTML 內文、HTML 屬性、JS 字串、URL 各自不同，所以沒辦法在輸入時就先做掉。

另外設定 `HttpOnly`，可能不會完全擋住 XSS 發生，但能讓攻擊者就算注入成功也偷不走 Cookie，可以做到降低災害的層面。

```ts
const cookieOptions: CookieOptions = {
    httpOnly: true, // 設定 HttpOnly
    sameSite: 'lax',
    secure: true,
    path: '/',
};
```

加入內容安全政策（CSP, Content Security Policy），透過 HTTP 回應標頭設定白名單，明確告訴瀏覽器哪些來源的指令碼、樣式或圖片可以載入與執行

```ts
// 使用 helmet 預設的 CSP 與其他安全標頭
app.use(
    helmet.contentSecurityPolicy({
        directives: {
            defaultSrc: ["'self'"], // 預設只能載入同源資源
            scriptSrc: ["'self'", 'trusted-cdn.com'], // 允許同源與指定 CDN 的 JS
            styleSrc: ["'self'", "'unsafe-inline'"], // 'unsafe-inline' 是為了相容既有 inline style 的妥協，能改用 nonce 就改
            objectSrc: ["'none'"], // 禁止 Flash 等物件
            upgradeInsecureRequests: [], // 自動將 HTTP 升級為 HTTPS
        },
    }),
);
```

#### AI 提示詞注入（Prompt Injection）

隨著 LLM 應用普及而出現，攻擊者透過隱藏式或引導式的語句問答，來讓 AI agent 回答機密資料，或聽從惡意指令。

說明防範之前，要先接受一個事實：

系統讀取輸入的內容後，雖然我們可以在問答的內容中，加入最高原則的問答規範來限制，但**寫在提示詞裡的規則是有機會被繞過的**。例如讓模型改用 base64、拆字、換一種語言講，規範可能就會失效了。

所以要將真正的邊界要放在工具層（tool），agent 能呼叫的每個 tool，本身就帶著使用者身分去查（`WHERE user_id = $1`），這樣就算模型被說服要撈別人的訂單，工具層也撈不到。

其次是縮小範圍：查訂單的 tool 就只回訂單欄位，不要順手把使用者資料一起帶出來。上線初期先只開放讀取，等多次測試、版本穩定後，再逐步放寬到寫入。

## 6. 不安全設計 Insecure Design

### 這個問題怎麼發生

不安全設計是強調「設計階段的缺陷」，與「實作層面的 Bug」不同，這意味著程式碼上寫得再完美，如果從業務邏輯或架構設計上就出錯，依然會被攻擊者利用。

舉個例子來說明：

> 設計註冊的 API `/register`

腦內模型通常是「一個真人填表單」。這個模型下，回饋清楚的錯誤訊息（例如已註冊過的會回應「此信箱已被註冊」），或是註冊後會插入的初始值、範例資料、甚至背後觸發各種外部動作（發信、建立雲端資源、呼叫第三方 API）等，這些都是為了用戶體驗好。

但這個設計沒有身份、沒有前情提要，任何人都能打。一旦把「一個真人」的假設換成「一支迴圈」，這兩個為了體驗設計的行為就變成攻擊面。

「此信箱已被註冊」這個提示會告訴攻擊者此信箱是存在的，可以嘗試登入破解；註冊後所做的初始行為，在海量的假身分註冊中會造成處理效率降低、資料庫的負擔、甚至發生系統崩潰。

### 在 Node.js 裡我會怎麼防

1. 在 `/register` 裝上 `express-rate-limit`，鍵值用 IP 來篩選。這能擋掉攻擊者「隨手寫個 for 迴圈打」的低成本濫用。
2. 考慮削弱體驗最佳化的部分，把「此信箱已被註冊」改成「已寄送確認信到該信箱」，但後端仍然可以判斷是否存在，再決定信件的發送。
3. 註冊後的預設操作，可以改動到「註冊後第一次登入」的事件集中，降低註冊時所需完成事項的後續處理。

## 7. 身分驗證失效 Authentication Failures

### 這個問題怎麼發生

1. 未提供或未強制執行多因子驗證（MFA）：系統僅依賴「帳號/密碼」作為唯一身分識別手段。一旦密碼因憑證填充、釣魚或社交工程攻擊洩漏，攻擊者便能無阻礙地直接登入。

2. Session / Token 管理缺陷：使用者登入後 Session ID 未重新產生，或是 JWT 簽署密鑰過弱、未驗證過期時間（exp），甚至將敏感資料直接曝露在 Token Payload 中。

3. 不安全的儲存：後端採用明碼或弱雜湊（如 MD5, SHA1）儲存密碼

4. 密碼設置流程過於簡單：沒有做弱密碼掃描、密碼長度不夠長，以及重置密碼時僅要求輸入像是「國小名稱」的安全提問等低熵（Low Entropy）且容易被社交工程猜出的資訊

### 在 Node.js 裡我會怎麼防

首先針對憑證填充攻擊與暴力破解，使用 `otplib` 與 `qrcode` 處理 TOTP（如 Google Authenticator / Authenticator App）的 Secret 產生與驗證。

```ts
import { authenticator } from 'otplib';
import qrcode from 'qrcode';

// 為使用者產生 TOTP Secret 並輸出 QRCode
export async function generateMfaSecret(userEmail: string) {
    const secret = authenticator.generateSecret();
    const otpauth = authenticator.keyuri(userEmail, 'appName', secret);
    const qrCodeUrl = await qrcode.toDataURL(otpauth);

    // 將 secret 加密後存入使用者資料庫（例如 user.mfaSecret），預設 user.mfaEnabled 為 false
    return { secret, qrCodeUrl };
}

// 驗證使用者輸入的 6 位數一次性密碼
export function verifyMfaToken(userSecret: string, token: string): boolean {
    try {
        return authenticator.verify({ token, secret: userSecret });
    } catch (error) {
        return false;
    }
}
```

另外在 API 閘道或路由加入阻擋爆破攻擊，可以使用`rateLimit`

```ts
import rateLimit from 'express-rate-limit';

export const loginLimiter = rateLimit({
    windowMs: 15 * 60 * 1000, // 15 分鐘
    max: 5, // 每 IP 限制 5 次嘗試
    message: {
        status: 429,
        message: '登入嘗試次數過多，請 15 分鐘後再試',
    },
    standardHeaders: true,
    legacyHeaders: false,
});

// 套用至登入路由
app.post('/api/v1/auth/login', loginLimiter, handleLogin);
```

在發放 Token 時需設定合理的過期時間，並透過 HTTP-Only Cookie 帶給前端，防止 XSS 竊取 Session。若採用 JWT（無狀態），Session Fixation 則不適用；若仍用傳統 Session，登入後要呼叫 `req.session.regenerate()` 來換發新 ID。

```ts
export function sendAuthToken(res: Response, userId: string) {
    // 簽發 JWT 並使用強密鑰與過期時間
    const token = jwt.sign(
        { userId },
        process.env.JWT_SECRET!, // 確保 Secret 為高強度亂數
        { expiresIn: '15m', algorithm: 'HS256' },
    );

    // 2. 寫入安全的 HttpOnly Cookie
    res.cookie('access_token', token, {
        httpOnly: true, // 防止 JS 讀取（防 XSS 竊取）
        secure: process.env.NODE_ENV === 'production', // 僅限 HTTPS
        sameSite: 'strict', // 防範 CSRF 攻擊，正常標準寫 'lax' 也可以
        maxAge: 15 * 60 * 1000,
    });
}
```

資料庫絕對不要對密碼做明碼的儲存，要採用 `argon2id` 或 `bcrypt` 等加鹽雜湊，並在登入時做驗證比對；密碼不一定要提高複雜度，但要避免使用像是`Password123`的弱密碼，且字串長建議要到達 12 碼以上，可以使用 `zod` 來做字串判斷。

```ts
// 註冊時：加密儲存
export async function hashPassword(password: string): Promise<string> {
    return await argon2.hash(password, {
        type: argon2.argon2id,
        memoryCost: 2 ** 16,
        timeCost: 3,
    });
}

// 登入時：安全比對
export async function verifyPassword(hash: string, password: string): Promise<boolean> {
    return await argon2.verify(hash, password);
}
```

最後避開安全提問的低熵，改採「密碼連結以信件寄送」的方式，並且連結附的 token 需一次性使用、短期過期、高熵隨機產生，來作爲更改密碼的方式

## 8. 軟體或資料完整性失效 Software or Data Integrity Failures

### 這個問題怎麼發生

發生在系統使用了未經驗證來源的軟體、套件更新、外掛，或是系統在發送關鍵資料時沒有確保其完整性。

可以分成三大類：

- 不安全的軟體供應鏈：Node.js 生態系中使用大量來自 `npm` 指令下載的資料，可能有植入後門程式或惡意程式碼，混入專案環境裡被執行
- Prototype Pollution 原型鏈污染：當不可信的 JSON（例如前端傳入的物件）被直接 merge 進既有物件，且鍵名未過濾 `__proto__` / `constructor.prototype` 時，攻擊者可污染全域原型鏈；另外像 `node-serialize` 這類套件會把字串還原成可執行函式，等同變相 `eval`。
- CI/CD Pipeline 與更新機制安全缺陷：CI/CD 部署流程缺乏原始碼簽章驗證、套件鎖定機制，或是更新發布管道未經加密與雜湊校驗，導致構建過程被中途竄改、資料竊取等

### 在 Node.js 裡我會怎麼防

針對軟體供應鏈，安裝套件一律用 `npm ci` 而非 `npm install`，強制依照 `package-lock.json` 裡鎖定的版本與 hash 安裝，避免被暗中置換成惡意版本；並在 CI 裡跑 `npm audit --audit-level=high` 擋掉已知漏洞套件，同時搭配 Dependabot 定期升版。

```json
// package.json
{
    "scripts": {
        "ci": "npm ci --ignore-scripts && npm audit --audit-level=high"
    }
}
```

`--ignore-scripts` 可以避免安裝時觸發套件裡惡意的 `postinstall` 腳本。

針對 Prototype Pollution，收到外部 JSON 後不要用會遞迴合併的函式（舊版 `lodash.merge` / `_.defaultsDeep`）直接套用在信任物件上，並在啟動時凍結 `Object.prototype` 作為最後一道防線；資料結構一律用 `zod` 驗證過再使用，不要把整包物件原封不動塞進系統。

```ts
import { z } from 'zod';

// 啟動時凍結，禁止任何程式碼往 Object.prototype 加東西
Object.freeze(Object.prototype);

const UserInputSchema = z.object({
    name: z.string(),
    age: z.number(),
});

export function parseUserInput(raw: unknown) {
    // 驗證失敗直接丟錯，不會把未知欄位（如 __proto__）帶入後續流程
    return UserInputSchema.parse(raw);
}
```

針對 CI/CD 與發布管道，建置產物要有完整性校驗（例如發佈時附上 SHA-256 checksum 或用 Sigstore/cosign 簽章），Pipeline 的 Secret 與部署權限採最小權限原則，避免第三方 Action / Plugin 有過大的寫入權限。

## 9. 安全日誌與警示失效 Security Logging and Alerting Failures

### 這個問題怎麼發生

安全日誌與警示失效（Security Logging and Alerting Failures）發生在系統無法紀錄關鍵的安全事件、日誌品質太差難以查證，或是就算寫了 Log 也沒人會在第一時間發現異常。

這種失效不會直接讓系統被入侵，但會讓攻擊者「進來之後沒人知道」。業界資安報告常提到，攻擊者入侵後平均可以潛伏數個月才被發現，核心原因通常是：

- **未記錄關鍵安全事件**：登入失敗、權限變更、密碼重置、高風險 API（如批次匯出資料）完全沒留 Log。
- **日誌品質差、沒集中管理**：Log 只印在單一機器上、格式是純文字而非結構化 JSON，缺乏 `traceId` / `userId` / `ip` 這些可追蹤欄位；也沒同步到中心化系統（如 ELK、Datadog），一旦這台機器被攻陷或重啟，證據就跟著消失。
- **沒有異常監測與即時告警**：Log 寫了但沒設規則，例如 1 分鐘內出現 500 次登入失敗，維運團隊完全不會收到通知。
- **Log 本身洩漏敏感資料**：直接把明碼密碼、信用卡號、JWT Token 印進 Log，讓 Log 系統本身變成新的資安破口。

### 在 Node.js 裡我會怎麼防

防禦分三層：結構化日誌、敏感資料遮蔽、集中傳輸與告警。

#### 1. 用 Pino 輸出結構化 JSON，並帶入 traceId

不要用 `console.log`，改用效能較好的 `pino` 輸出 JSON 格式，並透過 `AsyncLocalStorage` 讓同一個請求不管經過多少層非同步呼叫，都能拿到同一個 `traceId`，方便事後串起完整流程。

```ts
import pino from 'pino';
import { AsyncLocalStorage } from 'node:async_hooks';

export const asyncLocalStorage = new AsyncLocalStorage<{ traceId: string; userId?: string }>();

export const logger = pino({
    level: process.env.LOG_LEVEL || 'info',
    timestamp: pino.stdTimeFunctions.isoTime,
});

// 記錄安全事件的專用 helper
export function logSecurityEvent(event: string, details: Record<string, unknown>) {
    const store = asyncLocalStorage.getStore();

    logger.warn(
        {
            category: 'SECURITY',
            event,
            traceId: store?.traceId ?? 'N/A',
            userId: store?.userId ?? 'anonymous',
            ...details,
        },
        `[SECURITY EVENT] ${event}`,
    );
}
```

#### 2. Middleware 自動遮蔽敏感欄位

密碼、Token、信用卡號這類欄位絕對不能原封不動印進 Log，寫入前先用黑名單做遮蔽：

```ts
import type { NextFunction, Request, Response } from 'express';

const SENSITIVE_KEYS = new Set(['password', 'token', 'authorization', 'creditcard', 'secret']);

function sanitize(obj: unknown): unknown {
    if (!obj || typeof obj !== 'object') return obj;
    if (Array.isArray(obj)) return obj.map(sanitize);

    const result: Record<string, unknown> = {};
    for (const [key, value] of Object.entries(obj)) {
        result[key] = SENSITIVE_KEYS.has(key.toLowerCase()) ? '[REDACTED]' : sanitize(value);
    }
    return result;
}

export function requestLoggerMiddleware(req: Request, res: Response, next: NextFunction) {
    logger.info(
        {
            method: req.method,
            url: req.originalUrl,
            ip: req.ip,
            userAgent: req.get('user-agent'),
            body: sanitize(req.body),
        },
        'Incoming Request',
    );

    next();
}
```

黑名單式遮蔽的風險是「漏加欄位」——之後新增 `apiKey`、`refreshToken` 忘記補進 `SENSITIVE_KEYS` 就會漏印。更穩妥的做法是搭配 pino 內建的 `redact` 選項，用路徑（如 `req.headers.authorization`）指定要遮蔽的位置，而不是全靠自己維護一份清單。

#### 3. 集中傳輸 Log 並設定即時告警

前面兩步只解決了「Log 寫得乾不乾淨」，但 Log 若只留在本機，攻擊者入侵後照樣能刪掉滅證。實務上會用 `pino-transport`（或旁掛 Fluent Bit / Vector 之類的 agent）把 Log 即時傳到中心化系統（ELK、Datadog、S3 等），確保單機被攻陷也留有備份。

在關鍵驗證失敗點上，也要主動計數並觸發告警，而不是被動等人翻 Log：

```ts
export async function handleLoginFailure(req: Request, email: string, reason: string) {
    logSecurityEvent('AUTH_LOGIN_FAILED', {
        email,
        reason,
        ip: req.ip,
        userAgent: req.get('user-agent'),
    });

    // 短時間內同一 IP 失敗次數暴增時，推播到 Slack / PagerDuty
    if (await isHighRiskIp(req.ip)) {
        await sendSecurityAlertToSlack({
            title: '🚨 高風險登入異常告警',
            message: `IP: ${req.ip} 短時間內多次登入失敗，請確認是否為爆破攻擊。`,
        });
    }
}
```

## 10. 例外狀況處理不當 Mishandling of Exceptional Conditions

### 這個問題怎麼發生

例外狀況處理不當（Mishandling of Exceptional Conditions）是 OWASP Top 10:2025 新增的獨立分類，發生在系統面對非預期錯誤、異常輸入或程式崩潰時，沒有妥善捕捉與控制。

常見成因：

- **錯誤資訊過度揭露**：API 發生未捕捉的例外時，直接把完整的 Stack Trace、SQL 語法、內部檔案路徑回傳給前端，等於幫攻擊者畫出系統架構圖。
- **未處理的非同步錯誤讓程式崩潰**：Node.js 是非同步環境，`Promise` 被 reject 或事件監聽器裡拋出的錯誤如果沒被捕捉，會讓整個 process 無預警死掉，變成一種 DoS。
- **靜默吞掉錯誤**：用空的 `catch (e) {}` 把錯誤吃掉，系統進入不一致的狀態（例如扣款成功但訂單沒建立），且完全沒留紀錄可查。

### 在 Node.js 裡我會怎麼防

分三層來擋：統一錯誤回應、process 層級的保底防護、非同步錯誤不漏接。

#### 1. 統一的 Express 錯誤處理 Middleware

自訂一個「預期內的業務錯誤」型別，讓 Middleware 能分辨這是可預期的錯誤（該回什麼訊息給使用者）還是不可預期的例外（生產環境一律不能洩漏細節）。

```ts
export class AppError extends Error {
    constructor(
        public statusCode: number,
        message: string,
    ) {
        super(message);
        Error.captureStackTrace(this, this.constructor);
    }
}

export function globalErrorHandler(err: Error | AppError, req: Request, res: Response, _next: NextFunction) {
    const isProduction = process.env.NODE_ENV === 'production';
    const statusCode = err instanceof AppError ? err.statusCode : 500;

    logger.error({ err, url: req.originalUrl, method: req.method, ip: req.ip }, `[Unhandled Error] ${err.message}`);

    res.status(statusCode).json({
        status: 'error',
        // AppError 是我們自己丟出的，訊息可以放心給使用者看；其他未預期的錯誤一律用罐頭訊息，避免洩漏內部細節
        message: err instanceof AppError || !isProduction ? err.message : '系統發生內部錯誤，請稍後再試',
    });
}
```

#### 2. Process 層級攔截未捕捉例外

`uncaughtException` / `unhandledRejection` 觸發代表 process 已經進入不可預期的狀態，官方建議是記錄後盡快重啟，而不是硬撐著繼續跑：

```ts
process.on('unhandledRejection', (reason: Error) => {
    logger.fatal({ err: reason }, 'Unhandled Promise Rejection detected!');
    gracefulShutdown(1);
});

process.on('uncaughtException', (error: Error) => {
    logger.fatal({ err: error }, 'Uncaught Exception detected! Shutting down...');
    gracefulShutdown(1);
});

function gracefulShutdown(code: number) {
    // 停止接收新請求，等現有請求處理完再 exit，交給 PM2 / Kubernetes 之類的流程管理工具負責重啟
    server.close(() => process.exit(code));
}
```

#### 3. 非同步路由不漏接錯誤

如果專案還在用 Express 4，路由裡 `async` 函式拋出的錯誤不會自動被 Express 接住，需要包一層 wrapper 才會轉交給 `globalErrorHandler`：

```ts
export const catchAsync = (fn: (req: Request, res: Response, next: NextFunction) => Promise<unknown>) => {
    return (req: Request, res: Response, next: NextFunction) => {
        fn(req, res, next).catch(next);
    };
};

app.post(
    '/api/v1/payment',
    catchAsync(async (req, res) => {
        const result = await processPayment(req.body);

        if (!result.success) {
            throw new AppError(400, '交易失敗：付款卡號無效');
        }

        res.status(200).json({ status: 'success', data: result });
    }),
);
```

若是 Express 5（本文第 1 點用的版本），路由裡 `async` 函式拋出的錯誤會自動被接住並轉交給錯誤處理 Middleware，`catchAsync` 就不需要了——這裡列出來是給還在 Express 4 專案的讀者參考。
